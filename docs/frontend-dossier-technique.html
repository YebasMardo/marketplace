Comment lire ce document

Complément du Dossier technique du backend (backend-dossier-technique.html), qui documentait l'API avant que le frontend n'existe. Le frontend a depuis été largement entamé — ce document décrit l'état réel du code aujourd'hui, pas une recommandation abstraite. Il a deux lecteurs en tête :

  • Vous. Savoir précisément ce qui est déjà câblé, ce qui est une coquille vide, et ce qui n'existe pas encore — pour ne pas reconstruire ce qui existe, ni supposer câblé ce qui ne l'est pas.
  • Un agent IA à qui vous confierez la suite (panier, commandes, paiement). Les sections 3 (déjà fait), 4 (reste à faire) et 5 (conventions établies) sont écrites pour être données telles quelles comme contexte avant toute nouvelle fonctionnalité.
Le code existant a des conventions — respectez-les Plusieurs choix structurants (URL comme source de vérité pour les filtres, ajustement d'état pendant le rendu plutôt que via useEffect, schémas Zod miroir des DTO backend, tags RTK Query déjà réservés...) sont volontaires et cohérents sur tout le code déjà écrit. Un agent qui les ignore produira un code qui marche isolément mais détonne avec le reste. La section 5 les documente explicitement.

1. Vue d'ensemble & pile technique

SPA React consommant l'API NestJS documentée dans le dossier backend. Trois espaces cohabitent dans la même app, selon le rôle renvoyé par GET /auth/me : public (catalogue, fiche produit, auth), acheteur (panier, commandes) et vendeur (produits, ventes) — plus un espace admin pour les catégories.

Variables d'environnement

vite.config.ts pointe envDir vers la racine du repo (envDir: '../') : le frontend lit le .env à la racine, pas un frontend/.env séparé. Une seule variable est consommée aujourd'hui, dans lib/apiClient.ts : 

baseUrl: import.meta.env.VITE_API_URL   // ex. http://localhost:3000
VITE_API_URL n'est pas dans .env.example docker-compose.yml la passe déjà comme argument de build du service frontend (args: VITE_API_URL: ${VITE_API_URL}), mais le fichier .env.example à la racine ne la liste pas encore. Quiconque copie .env.example vers .env sans le savoir aura un frontend qui appelle une URL undefined. À ajouter à .env.example à la prochaine occasion.

2. Architecture du socle

Le socle (état global, client API, routage, guardes) est entièrement en place et stable.

Le store Redux (app/store.ts)

reducer: {
  [api.reducerPath]: api.reducer,   // RTK Query — tout l'état serveur
  auth: authReducer,                 // { token } — persisté dans localStorage
  wishlist: wishlistReducer,         // { ids } — persisté dans localStorage, jamais côté API
}

Pas de reducer cart ni orders : ces domaines n'ont pas d'état local, tout transite par le cache RTK Query une fois câblés.

Le client API (lib/apiClient.ts)

Un seul api RTK Query, dans lequel chaque feature injecte ses endpoints :

tagTypes: ['Me', 'Product', 'Category', 'Cart', 'Order'],
endpoints: () => ({}),
Le tag 'Order' est déjà réservé, mais inutilisé Il figure dans tagTypes depuis la mise en place du socle, en anticipation du module commandes. N'ajoutez pas un second tag pour la même chose ('Orders', 'MyOrders'…) — utilisez 'Order' tel quel pour rester cohérent avec 'Product' et 'Category'.

Deux comportements transverses, à ne pas dupliquer ailleurs :

  • Injection du token — prepareHeaders lit state.auth.token et pose Authorization: Bearer … sur chaque requête. Aucun appel individuel n'a à s'en soucier.
  • Déconnexion globale sur 401 — baseQueryWithAuth observe chaque réponse ; un 401 déclenche dispatch(logout()), qui vide le token et le localStorage. Conforme au constat du dossier backend : pas de refresh token, donc un 401 signifie toujours « session finie ».

Routage & guardes (routes/)

router.tsx déclare l'arbre complet, y compris les routes des pages encore vides (§4) — le routage n'est pas ce qui manque, seul le contenu de certaines pages l'est. Deux guards, composés comme des routes wrapper plutôt que vérifiés page par page :

GardeVérifieUtilisé pour
ProtectedRoutestate.auth.token (Redux, synchrone) Tout écran nécessitant d'être connecté, quel que soit le rôle : /cart, /checkout, /my-purchases, /orders/:id
RoleRouteuseGetMeQuery() (réseau, asynchrone) puis allowed.includes(me.role) Espaces vendeur (/seller/*) et admin (/admin/*)

RoleRoute rend null pendant le chargement de /auth/me plutôt que de rediriger prématurément — évite un flash de redirection avant que la réponse n'arrive. Reproduisez ce motif pour toute nouvelle route dépendant du rôle.

Design tokens (index.css)

Palette « noir & blanc moderne + un seul accent » définie via @theme : ink/ink-soft/ink-faint, paper/paper-raised/paper-sunken, line/line-strong, et l'accent clay/clay-dark/clay-soft — utilisé avec parcimonie (promotions, favoris, actions destructives). Deux courbes d'easing personnalisées (--ease-out, --ease-drawer) pour les transitions. Toute nouvelle UI doit consommer ces tokens plutôt que des couleurs Tailwind par défaut (gray-500, blue-600…), pour rester visuellement cohérente avec l'existant.

Une incohérence pré-existante à connaître lib/orderStatus.ts (écrit à l'avance pour le module commandes, voir §4) utilise des couleurs Tailwind par défaut (bg-amber-100 text-amber-800…) et non les tokens ink/clay. À l'usage, envisagez de les réaligner sur la palette du reste de l'app plutôt que de les copier tels quels dans un badge de statut.

3. Ce qui est déjà construit et fonctionnel

Légende : FAIT câblé de bout en bout, testé à l'usage · PARTIEL l'essentiel fonctionne, un morceau précis manque · COQUILLE route et fichier existent, contenu = texte "en cours de construction" · ABSENT rien n'existe, pas même le fichier.

3.1 Authentification FAIT

features/auth/authApi.ts expose login, register, getMe, logoutApi. Pages Login.tsx / Register.tsx entièrement câblées : validation Zod (lib/schemas.ts), soumission, dispatch(setToken(...)), redirection vers /, affichage d'erreur via getErrorMessage(). Partagent AuthLayout (panneau vitrine avec témoignages tournants, pages/public/authShowcase.ts). Les boutons de connexion sociale (Google/GitHub/Facebook) sont rendus mais disabled — le backend n'expose aucun flux OAuth, ils ne sont pas de faux boutons cliquables sans effet.

3.2 Catalogue public FAIT (hors action panier)

PageContenu
Home.tsxHero (3 tuiles), carrousel des catégories racines, grille des 8 derniers produits (useGetProductsQuery({ limit: 8 })), bloc acheteur/vendeur
ProductList.tsxCatalogue complet : recherche (debounce 350 ms), filtre par catégorie (arbre repliable), pagination — tout l'état vit dans l'URL (useSearchParams), pas de useState local pour les filtres. Tiroir de filtres en mobile, squelette de chargement

ProductCard.tsx (utilisée par Home, ProductList, Wishlist) affiche note et délai de livraison statiques (STATIC_RATING, STATIC_DELIVERY) — l'API ne fournit aucune donnée d'avis pour l'instant, ce n'est pas un bug à corriger sans d'abord décider si/comment le backend exposera des avis.

3.3 Catégories FAIT

features/categories/categoriesApi.ts couvre les 5 routes backend (list/get via getCategories, create/update/delete). Utilisé à trois endroits :

  • CategoriesMenu.tsx (en-tête) et Footer.tsx — lecture seule, construite depuis categoryTree.ts
  • CategoryFilterTree.tsx — arbre repliable du panneau de filtres, déplie automatiquement le chemin vers la catégorie sélectionnée
  • pages/admin/Categories.tsx — CRUD complet (création, édition inline, suppression avec affichage du message d'erreur backend tel quel si la catégorie contient des sous-catégories/produits), upload d'image via ImageUploader

features/categories/categoryTree.ts fournit trois fonctions pures et réutilisables : flattenCategoryTree (liste plate ordonnée avec profondeur, pour les <select>), buildCategoryTree (arbre réel, pour l'UI repliable), getAncestorIds (chemin vers une catégorie, pour déplier automatiquement). Toute nouvelle UI de catégories doit réutiliser ces fonctions plutôt que reparcourir Category[] à la main.

3.4 Espace vendeur — produits FAIT

features/products/productsApi.ts couvre l'intégralité des 7 routes produits.

  • MyProducts.tsx — liste, badge de statut, publier/dépublier (désactivé si suspended — c'est un statut de modération, cf. dossier backend §7 nº2), suppression, lien vers l'édition.
  • ProductEditor.tsx — création et édition dans le même composant. Reflète exactement la validation conditionnelle du backend (@ValidateIf) via un z.discriminatedUnion('type', […]) dans lib/schemas.ts : bascule physique/numérique = deux jeux de champs (stock/poids/livraison vs référence fichier/limite de téléchargement). Utilise le motif RHF values (et non defaultValues) pour peupler le formulaire une fois la requête d'édition résolue — voir §5.

Les tags RTK Query ({'{'} type: 'Product', id: 'LIST' {'}'} + un tag par produit) font que le catalogue public se rafraîchit automatiquement quand un vendeur publie ou modifie un produit — aucun code de synchronisation supplémentaire n'est nécessaire.

3.5 Upload d'image FAIT

features/upload/uploadApi.ts (une seule mutation, FormData avec le champ image attendu par Multer côté backend) + components/ui/ImageUploader.tsx, un composant générique (prévisualisation, suppression, dossier Cloudinary paramétrable via prop folder). Réutilisé tel quel par ProductEditor (marketplace/products) et Categories (marketplace/categories). Toute nouvelle fonctionnalité nécessitant un upload d'image doit réutiliser ce composant, pas en écrire un nouveau.

3.6 Favoris / Wishlist FAIT — entièrement client

features/wishlist/wishlistSlice.ts : aucune route /wishlist côté API — la liste ne stocke que des identifiants produit, persistés dans localStorage, exactement comme le token d'auth. ProductCard (bouton cœur) et pages/public/Wishlist.tsx (grille dédiée, un useGetProductQuery par entrée) sont câblés. Si l'API expose un jour une vraie liste de favoris côté serveur, seul ce fichier change — les composants consommateurs passent par les sélecteurs (selectWishlistIds, selectIsWishlisted), jamais par localStorage directement.

3.7 UI transverse FAIT

Header.tsx (recherche, navigation par rôle, badges panier/favoris), Footer.tsx, UserMenu.tsx (menu compte, liens filtrés par rôle), CategoriesMenu.tsx, Spinner, EmptyState. Le hook partagé lib/useDropdown.ts gère fermeture au clic extérieur / Échap / changement de route pour les deux menus déroulants de l'en-tête — à réutiliser pour tout nouveau menu du même type plutôt que de recoder la logique de fermeture.

4. Ce qui reste à construire

Trois domaines backend n'ont pas (ou quasiment pas) de contrepartie frontend : le panier, les commandes, les paiements. Le routage et les fichiers de page existent déjà pour la plupart (coquilles avec « Cette page est en cours de construction ») — ce qui manque, c'est la couche features/*Api.ts et le contenu réel des pages.

4.1 Panier PARTIEL — lecture seule uniquement

features/cart/cartApi.ts ne contient que getCart, utilisé aujourd'hui pour le seul badge de quantité de l'en-tête. Le backend expose pourtant les 5 routes (voir dossier backend §5.5) : 

GET    /cart                    — présent (getCart)
POST   /cart/items               — absent
PATCH  /cart/items/:productId    — absent
DELETE /cart/items/:productId    — absent
DELETE /cart                     — absent
Rappel utile du dossier backend Les cinq routes renvoient le panier complet recalculé — inutile de raffraîchir via invalidatesTags puis un second aller-retour réseau. Patchez directement le cache RTK Query dans onQueryStarted (updateQueryData('getCart', undefined, …)), ce qui rend aussi la mise à jour du badge de l'en-tête instantanée.

Conséquences visibles ailleurs dans le code, à corriger en même temps :

  • ProductCard.tsx — le bouton rond « Ajouter au panier » sous le prix est rendu et stylé mais n'a aucun onClick (commentaire : « statique, non branché »).
  • ProductDetail.tsx — commentaire explicite à la place du bouton d'action.
  • pages/buyer/Cart.tsx — coquille vide à remplir : liste des lignes, quantités modifiables, sous-totaux (déjà calculés côté backend, cf. CartItem.subtotal dans types/api.ts), bouton vers /checkout.

4.2 Commandes ABSENT — aucune couche API

features/orders/ n'existe pas. Le type Order est déjà défini dans types/api.ts (avec le commentaire rappelant les deux statuts terminaux), et lib/orderStatus.ts (labels français + couleurs + SUCCESSFUL_STATUSES) est déjà écrit et prêt à l'emploi — mais rien ne les consomme encore. À créer : 

features/orders/ordersApi.ts
  checkout            POST /orders/checkout            { paymentMethod } → Order[]
  getMyPurchases      GET  /orders/my-purchases         → Order[]
  getMySales          GET  /orders/my-sales             → Order[]  (seller)
  getOrder            GET  /orders/:id                  → Order
  shipOrder           PATCH /orders/:id/ship            (seller)
  confirmDelivery     PATCH /orders/:id/confirm-delivery
  cancelOrder         PATCH /orders/:id/cancel
Le piège structurant : le checkout renvoie un TABLEAU Rappel direct du dossier backend §6.1 — un panier avec des articles de plusieurs vendeurs (ou mêlant physique/numérique chez un même vendeur) produit plusieurs commandes en un seul appel. Checkout.tsx ne doit jamais faire const order = response[0] : il doit rediriger vers un récapitulatif listant toutes les commandes créées, chacune avec son propre montant et sa propre action de paiement. C'est la décision la plus structurante de toute cette étape — à trancher avant d'écrire le premier composant.

Pages coquilles concernées, à remplir une fois ordersApi en place :

  • Checkout.tsx — récapitulatif multi-commandes (voir encadré ci-dessus)
  • MyPurchases.tsx / MySales.tsx — listes, à afficher avec ORDER_STATUS_LABELS/ORDER_STATUS_COLORS déjà prêts dans lib/orderStatus.ts plutôt que de redéfinir des libellés
  • OrderDetail.tsx — détail + actions selon rôle et statut (expédier, confirmer réception, annuler) — les transitions valides sont documentées dans le dossier backend §6.2, ne pas réinventer la machine à états côté client sans s'y référer

4.3 Paiements ABSENT — aucune couche API, dépendances non installées

features/payments/ n'existe pas non plus. Deux routes à couvrir : 

POST  /payments/:orderId/create-intent    (buyer)  → { clientSecret }
PATCH /payments/:orderId/confirm-cash     (seller) → déclenche markAsPaid()

Le paiement carte est le plus gros morceau restant :

  1. Installer @stripe/stripe-js et @stripe/react-stripe-js (absents de package.json aujourd'hui).
  2. Ajouter la clé publique Stripe côté frontend (une nouvelle variable VITE_STRIPE_PUBLISHABLE_KEY ou équivalent — n'existe pas encore, à distinguer de STRIPE_SECRET_KEY qui, elle, reste strictement côté backend).
  3. Le webhook (POST /payments/webhook) n'est jamais appelé par le frontend — c'est Stripe qui le fait. Après confirmation côté client via Stripe.js, la commande n'est pas immédiatement processing : le dossier backend §6.3 recommande un état d'attente (« paiement en cours de confirmation »), pas une redirection qui suppose le statut déjà à jour.

Le paiement en espèces est plus simple et ne nécessite aucune dépendance nouvelle : un simple bouton « Confirmer réception des espèces » côté vendeur, sur la fiche commande, appelant confirm-cash.

4.4 Tableau de bord vendeur COQUILLE

Dashboard.tsx est vide. Le backend n'expose aucune route d'agrégats dédiée (pas de /seller/stats ou équivalent) — les deux seules sources disponibles sont GET /products/mine (déjà câblé) et GET /orders/my-sales (à câbler, §4.2). Le tableau de bord devra donc calculer ses indicateurs (nombre de produits actifs, commandes en attente, chiffre d'affaires...) côté client à partir de ces deux listes, plutôt que de chercher une route d'agrégats qui n'existe pas.

5. Conventions établies à respecter

Ces motifs reviennent systématiquement dans le code déjà écrit. Les ignorer produit du code qui fonctionne mais rompt la cohérence — et complique la maintenance pour la prochaine personne (humaine ou agent) qui lira le fichier suivant.

1. Une tranche verticale par domaine, injectée dans l'api unique

// features/<domaine>/<domaine>Api.ts
export const xApi = api.injectEndpoints({ endpoints: (builder) => ({ ... }) });
export const { useXQuery, useYMutation } = xApi;

Jamais un second createApi — tout passe par le même client (lib/apiClient.ts) pour partager le cache, les tags et la gestion du 401.

2. Les schémas Zod sont un miroir exact des DTO backend

lib/schemas.ts reproduit fidèlement la validation conditionnelle du backend (@ValidateIf ↔ z.discriminatedUnion). Si un DTO backend change, le schéma Zod correspondant doit changer avec lui — un décalage produit soit des 400 côté backend (champ manquant), soit des rejets côté frontend pour des données que l'API accepterait.

3. L'état de filtrage/recherche vit dans l'URL, pas dans un useState

ProductList.tsx pilote tout (catégorie, recherche, page) via useSearchParams : lien partageable, bouton « précédent » qui fonctionne, F5 qui ne perd rien. Tout nouvel écran avec filtres/pagination (une future liste de commandes, par exemple) doit suivre le même motif plutôt que réinventer un état local.

4. Ajustement pendant le rendu plutôt que useEffect + setState

Motif répété trois fois dans le code existant (useDropdown, CategoryFilterTree, le champ de recherche de ProductList) pour synchroniser un état local sur une prop/URL qui change : comparer la valeur courante à une valeur mémorisée pendant le rendu, et ajuster immédiatement si elles divergent — pas dans un useEffect, qui provoquerait un rendu supplémentaire en cascade. C'est le motif React officiellement recommandé pour ce cas ; le réutiliser plutôt que repartir sur un useEffect classique.

5. Formulaires d'édition alimentés en asynchrone : values, pas defaultValues

ProductEditor.tsx utilise l'option values de React Hook Form pour peupler le formulaire une fois que useGetProductQuery a répondu — contrairement à defaultValues, qui ne se réévalue pas quand la donnée arrive après le premier rendu. Tout futur formulaire d'édition (une commande, un profil…) doit suivre le même motif.

6. Les erreurs API passent toutes par getErrorMessage()

lib/errorUtils.ts centralise l'extraction d'un message lisible depuis une erreur RTK Query (réseau, timeout, ou {'{'} message, statusCode {'}'} renvoyé par Nest, y compris quand message est un tableau — cas class-validator). Ne pas réinterpréter error.data à la main dans un composant.

7. Duplicité peuplé / brut sur sellerId et categoryId

Reflet direct d'un choix backend documenté (dossier backend §7 nº8) : ces deux champs sont des string bruts sur certaines routes et des objets peuplés ({'{'} _id, name, ... {'}'}) sur d'autres. types/api.ts les type en union (string | {'{'} ... {'}'}) — tout code qui les lit doit garder le typeof === 'object', comme le fait déjà ProductDetail.tsx, plutôt que de supposer un seul des deux formats.

6. Pièges connus & points de vigilance

Les boutons « Ajouter au panier » existent visuellement mais ne font rien Sur ProductCard (grille catalogue/accueil/favoris) et absent sur ProductDetail. Un test manuel superficiel du catalogue donne l'impression que « tout marche » jusqu'à cliquer sur ce bouton précis. Premier réflexe en reprenant ce projet : vérifier ce bouton avant de supposer le panier fonctionnel.
Pas de fusion panier anonyme ↔ panier serveur Le panier backend est lié au compte (cart:<userId> dans Redis, JWT requis sur toutes les routes /cart) — un visiteur non connecté ne peut rien y mettre. useGetCartQuery est déjà appelé avec skip: !token dans le Header, donc ce cas est déjà anticipé pour la lecture. Mais rien ne prépare une fusion d'un panier localStorage constitué hors connexion — si ce comportement est souhaité, c'est un choix produit à trancher avant d'écrire Cart.tsx, pas un détail d'implémentation à improviser en cours de route.
Deux statuts terminaux pour une commande « réussie » delivered (physique) et completed (numérique) signifient tous deux « commande aboutie ». lib/orderStatus.ts exporte déjà SUCCESSFUL_STATUSES = ['delivered', 'completed'] précisément pour éviter qu'un filtre sur 'completed' seul ne fasse disparaître silencieusement toutes les commandes physiques livrées d'une liste. Utilisez cette constante, ne la redupliquez pas.
Le rôle n'est qu'une question d'affichage côté client RoleRoute empêche d'atteindre une page, mais rien n'empêche un accès direct à l'API si le token est copié — c'est le backend, via RolesGuard, qui fait réellement autorité. Ne traitez jamais une vérification de rôle frontend comme une mesure de sécurité ; elle sert uniquement l'expérience utilisateur (ne pas montrer un lien vers un écran refusé).

7. Ordre de construction suggéré pour la suite

Suite logique de ce qui est déjà bâti — même logique de dépendances que le dossier backend §8 (« Ordre de construction suggéré »), dont les quatre premières étapes (socle, auth, catalogue public, espace vendeur) sont déjà couvertes par ce qui existe.

  1. Panier : les 4 mutations manquantes dans cartApi.ts (avec patch de cache via onQueryStarted, §4.1), puis brancher les boutons ProductCard/ProductDetail, puis construire Cart.tsx (lignes, quantités, sous-totaux déjà calculés par l'API).
  2. Checkout : ordersApi.checkout, puis Checkout.tsx — en traitant explicitement le tableau de commandes retourné (§4.2, encadré). C'est l'étape la plus structurante : une mauvaise supposition ici (une seule commande) se répercute sur tout ce qui suit.
  3. Commandes : le reste d'ordersApi.ts (my-purchases, my-sales, :id, transitions de statut), puis MyPurchases.tsx, MySales.tsx, OrderDetail.tsx — en s'appuyant sur lib/orderStatus.ts déjà écrit plutôt qu'en redéfinissant des libellés de statut.
  4. Tableau de bord vendeur : Dashboard.tsx, en agrégeant côté client depuis getMyProducts (existant) et getMySales (étape 3) — rappel : pas de route d'agrégats côté backend (§4.4).
  5. Paiement : en dernier, comme le recommandait déjà le dossier backend — c'est le plus dépendant de tout le reste (une commande doit exister avant de créer un intent) et le seul qui nécessite d'installer de nouvelles dépendances (§4.3). Espèces d'abord (un bouton, aucune dépendance nouvelle), Stripe ensuite.
En résumé Le socle (store, routage, client API, design system) et quatre domaines complets (authentification, catalogue, catégories, gestion des produits vendeur) sont solides et n'ont pas besoin d'être retouchés pour continuer. Ce qui reste — panier, commandes, paiements — a déjà ses types, son routage et, pour les commandes, ses libellés de statut préparés à l'avance. Le travail restant est réel mais cadré : suivre l'ordre ci-dessus évite de buter sur une dépendance manquante à mi-chemin.
