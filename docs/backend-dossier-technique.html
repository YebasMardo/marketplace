1. Vue d'ensemble & pile technique

Il s'agit d'une marketplace multi-vendeurs. Trois rôles cohabitent — admin, seller, buyer — et le catalogue distingue deux natures de produits : physiques (avec stock et expédition) et numériques (livrés par email après paiement). Cette distinction traverse tout le système : elle change le schéma du produit, le découpage des commandes, et le cycle de vie d'une commande.

MongoDB n'est pas dans le docker-compose Seul Redis est conteneurisé. La base Mongo est attendue en externe via MONGO_URI — vraisemblablement un cluster MongoDB Atlas, au vu du format de l'exemple dans .env.example.

Configuration d'amorçage (src/main.ts)

const app = await NestFactory.create(AppModule, { rawBody: true });

app.useGlobalPipes(new ValidationPipe({
  whitelist: true,             // supprime tout champ non déclaré dans le DTO
  forbidNonWhitelisted: true,  // ...et rejette carrément la requête (400)
  transform: true,             // convertit le JSON brut en instance de classe DTO
}));

await app.listen(3000);

Deux conséquences directes et importantes pour le frontend :

  • rawBody: true conserve le Buffer brut de chaque requête. C'est indispensable à Stripe : constructEvent() vérifie la signature sur les octets exacts reçus, pas sur le JSON reparsé.
  • forbidNonWhitelisted: true est impitoyable. Si votre formulaire React envoie ne serait-ce qu'un champ en trop — un confirmPassword, un _id renvoyé tel quel après un GET — l'API répond 400 Bad Request. Nettoyez systématiquement vos payloads avant envoi.
CORS est activé app.enableCors({ origin: process.env.FRONTEND_URL || 'http://localhost:5173', credentials: true }). Le || est délibéré : docker-compose définit une variable absente à la chaîne vide, que ?? ne rattraperait pas — l'origine autorisée serait alors "".

2. Architecture en modules

Onze modules, dont deux marqués @Global() — RedisModule et EmailModule. Être global signifie que n'importe quel module peut injecter RedisService ou EmailService sans réimporter le module parent à chaque fois. C'est justifié ici : ces deux services sont transverses et utilisés par des fonctionnalités sans lien entre elles. 

AppModule
├── ConfigModule (global)         variables d'environnement
├── MongooseModule.forRootAsync   connexion Mongo différée jusqu'à ConfigService
│
├── RedisModule      @Global      panier + liste noire des tokens
├── EmailModule      @Global      Resend : bienvenue, livraison numérique
│
├── UsersModule                   modèle User, aucun contrôleur exposé
├── AuthModule       ← Users      register / login / me / logout
├── CategoriesModule              arbre de catégories (admin)
├── ProductsModule                catalogue (seller)
├── UploadModule                  Cloudinary
├── CartModule       ← Products, Redis
├── OrdersModule     ← Cart, Products, Users, Email
└── PaymentsModule   ← Orders     Stripe + espèces

Le sens des dépendances

La chaîne se lit de gauche à droite et ne remonte jamais : Payments → Orders → Cart → Products. Aucune dépendance circulaire, ce qui est sain — ProductsService ignore totalement l'existence des commandes.

Deux points de conception qui méritent d'être soulignés, parce qu'ils sont corrects et volontaires :

  • UsersModule n'expose aucun contrôleur. Il n'existe donc aucune route /users. C'est un module de service pur, consommé par Auth et Orders. Les informations de l'utilisateur connecté passent exclusivement par GET /auth/me.
  • markAsPaid() vit dans OrdersService, pas dans PaymentsService. C'est l'unique porte d'entrée par laquelle une commande devient payée, que le déclencheur soit le webhook Stripe ou la confirmation manuelle d'un paiement en espèces. Une seule règle métier, un seul endroit — les deux modes de paiement ne peuvent pas diverger.

3. Modèles de données

3.1 User

Collection users, horodatage automatique (timestamps: true).

ChampTypeContraintes & remarques

passwordHashstringrequis — hash bcrypt (coût 10). Le mot de passe brut n'est jamais stocké

Le rôle est choisi librement à l'inscription RegisterDto accepte role: 'buyer' | 'seller'. N'importe qui peut donc devenir vendeur en cochant une case. admin est exclu du DTO — un compte administrateur doit être créé manuellement en base. Pour un MVP c'est acceptable, mais gardez-le en tête.

3.2 Category

Arbre de catégories à profondeur libre, via un simple parentId auto-référencé.

ChampTypeContraintes & remarques
namestringrequis, trim
slugstringrequis, unique — généré automatiquement depuis name
parentIdObjectId | nullnull = catégorie racine

Le slugify() maison passe en minuscules, retire les accents par normalisation NFD (é → e), et remplace tout caractère hors a-z0-9 par un tiret. « Électroménager & Cuisine » devient electromenager-cuisine.

Le slug est généré mais jamais utilisé pour la lecture Toutes les routes fonctionnent par ObjectId : GET /categories/:id. Il n'existe aucun GET /categories/slug/:slug. Si vous voulez des URLs propres côté frontend (/c/electromenager), il faudra soit ajouter cette route au backend, soit charger toutes les catégories au démarrage et résoudre le slug → id côté client. Vu leur faible nombre, la seconde option est tout à fait viable.

La validation conditionnelle

CreateProductDto utilise @ValidateIf() pour n'exiger les champs que lorsqu'ils sont pertinents : 

@ValidateIf((dto) => dto.type === 'physical')
@IsInt() @Min(0)
stock?: number;

@ValidateIf((dto) => dto.type === 'digital')
@IsString() @IsNotEmpty()
fileKey?: string;

Le frontend doit refléter exactement cette logique : un formulaire produit où le choix physique / numérique bascule deux jeux de champs distincts. Envoyer stock sur un produit numérique déclenchera une erreur 400, puisque forbidNonWhitelisted est actif.

3.4 Order, OrderItem & ShippingDetails

Une commande représente un vendeur et une seule nature de produit. C'est la décision structurante de tout le système de commandes : un panier contenant des articles de trois vendeurs différents produit trois commandes distinctes.

OrderItem — un instantané figé

Sous-document déclaré avec @Schema({ _id: false }) : les lignes ne sont jamais éditées ni recherchées individuellement, elles n'ont donc pas besoin d'identité propre.

ChampTypeRemarques
productIdObjectId → Productrequis
titlestringCopie du titre au moment de l'achat
pricenumberCopie du prix au moment de l'achat
quantitynumber≥ 1
Pourquoi dupliquer titre et prix plutôt que faire un populate ? Parce qu'une commande est un document historique. Si le vendeur baisse son prix la semaine suivante, une commande passée ne doit pas voir son montant réécrit rétroactivement. Le total stocké resterait alors incohérent avec la somme de ses lignes. C'est un bon réflexe de conception, et il est appliqué correctement ici.

Sous-document @Schema({ _id: false }), pour la même raison qu'OrderItem : aucune identité propre. Renseigné par OrdersService.checkout() sur chacune des commandes issues d'un même panier — chaque commande porte donc sa propre copie.

Pourquoi shipping n'est-il pas required ? Parce que les commandes créées avant l'ajout du formulaire de livraison n'en ont pas, et que Mongoose valide le document entier à chaque save() : le rendre obligatoire ferait échouer cancel(), markAsShipped() et markAsPaid() sur ces commandes-là. Toute lecture doit donc tester sa présence avant affichage. Un required: true ne redeviendra envisageable qu'après une migration des documents existants.

3.5 Le panier : pourquoi il vit dans Redis

Le panier n'a aucune collection MongoDB. Il est stocké sous la clé cart:<userId> avec une durée de vie de 7 jours, réinitialisée à chaque écriture. La valeur stockée est volontairement minimale : 

// clé : cart:66f1a2b3c4d5e6f7a8b9c0d1
{ "66a1...": 2, "66b2...": 1 }   // productId → quantité

À la lecture, getCart() enrichit cette carte brute en allant chercher title, price et images en base pour chaque produit, puis calcule les sous-totaux. Le panier renvoie donc toujours des prix à jour, jamais un instantané périmé — exactement l'inverse de OrderItem, et c'est volontaire dans les deux cas.

Autre détail soigné : si un produit a été supprimé entre-temps, findOne() lève une NotFoundException, qui est rattrapée. L'article est retiré du panier, le panier est resauvegardé, et la requête aboutit normalement au lieu de planter. 

try {
  const product = await this.productsService.findOne(productId);
  items.push({ /* ... */ });
} catch {
  delete cart[productId];   // produit disparu → on l'oublie silencieusement
  cartChanged = true;
}
Conséquence directe pour le frontend Le panier est lié au compte utilisateur, pas au navigateur. Un visiteur non connecté ne peut rien mettre au panier : toutes les routes /cart exigent un JWT. Deux options s'offrent à vous — soit exiger la connexion avant tout ajout, soit maintenir un panier local (localStorage) fusionné avec le panier serveur au moment du login. La seconde offre une bien meilleure expérience, mais c'est du travail purement frontend : le backend ne vous aidera pas.

4. Authentification & autorisation

Le parcours d'un token

  1. POST /auth/register ou /auth/login renvoie { access_token }.
  2. La charge utile signée est minimale : { sub: userId, role }, valable 7 jours.
  3. Le frontend le renvoie ensuite sur chaque appel protégé : Authorization: Bearer <token>.
  4. JwtStrategy.validate() vérifie la signature, l'expiration, puis la liste noire Redis, et pose { userId, role } sur req.user.
  5. Les contrôleurs y accèdent via le décorateur @CurrentUser().
Aucun refresh token Un seul token, 7 jours, non renouvelable. Passé ce délai, l'utilisateur est déconnecté sans préavis. Le frontend doit intercepter les 401 globalement, purger l'état d'authentification et rediriger vers la page de connexion.

Les deux gardes

GardeComportement
JwtAuthGuard Étend AuthGuard('jwt') de Passport. Rejette en 401 si le token est absent, mal signé, expiré ou révoqué.
RolesGuard Lit les métadonnées posées par @Roles(...) via le Reflector. Sans @Roles() sur la route, il laisse passer tout utilisateur authentifié. Rejette en 403 sinon.
L'ordre de déclaration compte @UseGuards(JwtAuthGuard, RolesGuard) — dans cet ordre précis. RolesGuard lit request.user.role, qui n'existe que si JwtAuthGuard s'est exécuté avant. Inversés, user serait undefined et l'accès serait refusé systématiquement.

La révocation à la déconnexion

Un JWT est par nature sans état : le serveur ne peut pas « l'oublier ». Une déconnexion qui se contenterait de supprimer le token côté navigateur laisserait un token parfaitement valide pendant 7 jours à quiconque en aurait fait une copie. La parade retenue est une liste noire dans Redis : 

async logout(token: string) {
  const decoded = this.jwtService.decode(token) as { exp?: number } | null;
  const ttlSeconds = decoded?.exp ? decoded.exp - Math.floor(Date.now() / 1000) : 0;

  if (ttlSeconds > 0) {
    await this.redisService.set(`auth:blacklist:${token}`, '1', ttlSeconds);
  }
  return { message: 'Déconnecté avec succès' };
}

La finesse est dans le TTL : la clé Redis expire exactement quand le token lui-même expire. La liste noire ne peut donc pas grossir indéfiniment — elle se purge seule. Côté vérification, JwtStrategy consulte cette liste à chaque requête : 

async validate(req: Request, payload: JwtPayload) {
  const token = ExtractJwt.fromAuthHeaderAsBearerToken()(req);
  const blacklisted = token && (await this.redisService.get(`auth:blacklist:${token}`));
  if (blacklisted) {
    throw new UnauthorizedException('Session expirée, veuillez vous reconnecter');
  }
  return { userId: payload.sub, role: payload.role };
}

C'est passReqToCallback: true dans le constructeur de la stratégie qui donne accès à la requête brute, et donc au token d'origine — la charge décodée seule ne suffirait pas.

Les emails transactionnels

Deux messages sont envoyés via Resend, tous deux en français :

MéthodeDéclencheurContenu
sendWelcomeEmail() AuthService.register() Message de bienvenue, personnalisé avec le prénom si fourni
sendDigitalDelivery() OrdersService.markAsPaid(), uniquement si fulfillmentType === 'digital' Un email par article, contenant le lien de téléchargement
L'envoi d'email n'est pas protégé contre l'échec register() fait await this.emailService.sendWelcomeEmail(...) sans try/catch. Si Resend est indisponible ou la clé API invalide, l'inscription entière échoue alors que le compte vient d'être créé en base. L'utilisateur voit une erreur mais son compte existe — il ne pourra pas se réinscrire (409 Conflict). Un try/catch avec journalisation serait préférable : l'email de bienvenue n'est pas critique au point de bloquer une inscription.

5. Référence complète de l'API

Base : http://localhost:3000 — aucun préfixe global. Les routes sont exposées à la racine (/auth/login, et non /api/auth/login). Légende : PUBLIC aucune authentification · JWT token requis · RÔLE rôle spécifique exigé.

MéthodeRouteAccèsCorps & réponse

Sur PATCH et DELETE, un produit appartenant à un autre vendeur renvoie 404 et non 403 — le filtre porte sur sellerId, donc rien n'est trouvé. C'est défendable (on ne révèle pas l'existence de la ressource), mais le message d'erreur, lui, précise « ou vous n'en êtes pas le vendeur », ce qui annule ce bénéfice.

5.5 Panier — /cart

@UseGuards(JwtAuthGuard) est posé sur la classe entière : toutes les routes exigent un token.

MéthodeRouteCorps & réponse
GET/cart → { items: [{ productId, quantity, title, price, originalPrice?, images, subtotal, type }], total }. price est le montant réellement facturé ; originalPrice n'apparaît qu'en cas de promotion, pour le prix barré ; type (physical | digital) permet au checkout de savoir s'il doit exiger une adresse postale
POST/cart/items { productId, quantity ≥ 1 }. Quantité ajoutée à l'existante. 404 si le produit n'existe pas. Renvoie le panier complet
PATCH/cart/items/:productId { quantity ≥ 0 }. Quantité remplacée. 0 retire l'article. Renvoie le panier complet
DELETE/cart/items/:productId Retire l'article. Renvoie le panier complet
DELETE/cart Vide le panier → { items: [], total: 0 }
Bonne nouvelle pour la gestion d'état Les cinq routes renvoient le panier complet recalculé. Vous n'avez donc jamais besoin de refaire un GET /cart après une mutation : la réponse est l'état à jour. Avec RTK Query, cela se traduit par une mise à jour directe du cache (updateQueryData) plutôt qu'une invalidation suivie d'un rechargement.

6. Les flux métier de bout en bout

6.1 Le découpage du panier en commandes

C'est la mécanique la plus importante à comprendre avant de dessiner l'écran de commande. checkout() regroupe les articles du panier par clé composite `${sellerId}:${type}`, et crée une commande par groupe. 

Panier de l'acheteur
├── Clavier mécanique   — vendeur A, physique
├── Souris gamer        — vendeur A, physique
├── Ebook « NestJS »    — vendeur A, numérique
└── Tapis de souris     — vendeur B, physique

        ↓ POST /orders/checkout

3 commandes distinctes, chacune avec son propre statut :
├── Commande 1 · vendeur A · physical · [Clavier, Souris]
├── Commande 2 · vendeur A · digital  · [Ebook]
└── Commande 3 · vendeur B · physical · [Tapis]
Trois commandes, donc trois paiements séparés Un seul « passer commande » côté utilisateur produit N commandes, chacune avec son propre total et son propre PaymentIntent Stripe. Le frontend doit gérer ce cas : soit enchaîner les paiements, soit présenter une page récapitulative listant les commandes créées avec un bouton « Payer » par ligne. C'est une contrainte structurelle, pas un détail d'implémentation — anticipez-la dès la maquette.

C'est également pendant cette boucle que le stock est réservé, article par article, pour les seuls produits physiques. Si un seul article manque, tout le checkout est refusé en 400 et les réservations déjà prises sont rendues — on n'obtient jamais une commande partielle. Voir §7 nº 5 pour le détail du mécanisme de compensation.

              ┌───────────────┴───────────────┐
              │                               │
       fulfillmentType                 fulfillmentType

                                              │

StatutConcerneSignification

Notez l'asymétrie : le parcours physique se termine sur delivered, le parcours numérique sur completed. Deux statuts terminaux différents pour un même concept de « commande aboutie ». Votre affichage frontend doit traiter les deux comme un succès — ne filtrez pas sur completed seul, vous manqueriez toutes les commandes physiques.

6.3 Paiement par carte (Stripe)

Frontend                    Backend                       Stripe
   │                           │                            │
   ├─ POST /orders/checkout ──▶│                            │
   │◀── [ Order(s) ] ──────────┤                            │
   │                           │                            │
   ├─ POST /payments/:id/      │                            │
   │       create-intent ─────▶├─ paymentIntents.create ───▶│
   │                           │◀── intent (client_secret) ─┤
   │                           ├─ stocke intent.id          │
   │◀── { clientSecret } ──────┤    sur la commande         │
   │                           │                            │
   ├─ Stripe.js confirme le paiement (carte saisie) ───────▶│
   │                           │                            │
   │                           │◀── POST /payments/webhook ─┤
   │                           │    payment_intent.succeeded│
   │                           ├─ vérifie la signature      │
   │                           ├─ markAsPaid(orderId)       │
   │                           ├─ ✉ si numérique            │
   │                           │                            │

Trois points à retenir pour l'implémentation frontend :

  • L'orderId voyage dans metadata du PaymentIntent. C'est ainsi que le webhook retrouve la commande — le frontend n'a rien à faire pour cela.
  • Les montants sont convertis en centimes (Math.round(total * 100)), comme l'exige Stripe.
  • Le webhook est asynchrone. Quand Stripe.js confirme côté client, la commande n'est pas encore passée en processing — le webhook peut arriver une ou deux secondes plus tard. Ne redirigez pas vers une page qui affiche le statut brut en supposant qu'il est déjà à jour ; prévoyez un état « paiement en cours de confirmation », avec relance périodique ou message d'attente.
L'idempotence est correctement gérée markAsPaid() commence par if (order.status !== 'pending_payment') return order;. Stripe pouvant livrer un même webhook plusieurs fois, cette garde évite qu'une commande soit traitée deux fois et que les emails de livraison numérique partent en double.

6.4 Paiement en espèces

Beaucoup plus simple, et pensé pour la remise en main propre. La commande est créée en pending_payment, puis le vendeur appelle PATCH /payments/:orderId/confirm-cash après avoir reçu l'argent. Le même markAsPaid() est invoqué — donc rigoureusement le même comportement en aval, y compris l'envoi des emails pour les produits numériques.

Une faiblesse de confiance à connaître Rien ne vérifie que l'acheteur a réellement payé. Le vendeur seul atteste. Pour un MVP entre utilisateurs qui se rencontrent, cela se défend ; à terme, une double confirmation acheteur + vendeur serait plus robuste.

6.5 Livraison d'un produit numérique

Déclenchée automatiquement dans markAsPaid() lorsque fulfillmentType === 'digital'. La méthode privée deliverDigitalItems() récupère l'acheteur, parcourt les lignes de commande et envoie un email par article possédant un fileKey.

Le fileKey est envoyé tel quel comme lien sendDigitalDelivery(buyer.email, item.title, product.fileKey) — le troisième paramètre s'appelle downloadUrl et atterrit directement dans un <a href>. Or le schéma décrit explicitement fileKey comme « référence de stockage, jamais une URL publique ». Il manque la couche qui transforme cette référence en URL signée à durée limitée. De plus, downloadLimit est stocké mais aucun compteur ne le fait respecter : le lien est réutilisable indéfiniment et partageable.

7. Corrections appliquées

Les huit points relevés lors de l'audit initial ont tous été corrigés. Cette section décrit ce qui a changé et pourquoi — elle vaut autant comme journal de décisions que comme vérification. L'ensemble a été validé par 39 tests de bout en bout contre la pile réelle (Mongo, Redis, API).

✅ Nº 1 — CORS activé

// src/main.ts
app.enableCors({
  origin: process.env.FRONTEND_URL || 'http://localhost:5173',
  credentials: true,
});

FRONTEND_URL a été ajouté à .env.example et au docker-compose.yml. Le choix de || plutôt que ?? est volontaire : docker-compose transmet une chaîne vide lorsqu'une variable est absente du .env, et ?? ne rattrape que null et undefined — l'origine autorisée aurait alors été "", bloquant tout.

✅ Nº 2 — Publication des produits

Une route dédiée a été retenue plutôt que l'ouverture du champ status dans le DTO : publier est une action métier distincte d'une édition de contenu, et elle mérite son propre bouton dans l'interface. 

PATCH /products/:id/status     { status: 'draft' | 'active' }

'suspended' est délibérément absent de UpdateProductStatusDto : c'est un statut de modération, il n'appartient pas au vendeur de se suspendre ou de se réactiver lui-même. Une tentative renvoie un 400. La route filtre sur { _id, sellerId }, donc un vendeur ne peut publier que ses propres produits.

✅ Nº 3 — Tableau de bord vendeur

GET /products/mine      → tous statuts, brouillons inclus

Déclarée avant @Get(':id') dans le contrôleur — le journal de démarrage confirme l'ordre de résolution : 

Mapped {/products, GET} route
Mapped {/products/mine, GET} route      ← avant
Mapped {/products/:id, GET} route       ← après

Contrairement au catalogue public, cette route renvoie un tableau simple et non paginé : un vendeur gère un nombre de produits qui tient sur un écran, et la pagination compliquerait inutilement l'interface de gestion.

✅ Nº 4 — Upload verrouillé

@UseGuards(JwtAuthGuard, RolesGuard)
@Roles('seller')
@UseInterceptors(FileInterceptor('image', {
  limits: { fileSize: 5 * 1024 * 1024 },
  fileFilter: (_req, file, cb) => {
    if (!/^image\/(jpeg|png|webp)$/.test(file.mimetype)) {
      return cb(new BadRequestException('Format non supporté…'), false);
    }
    cb(null, true);
  },
}))

Passer une erreur au callback plutôt que cb(null, false) produit un 400 explicite. Avec false, Multer écarte silencieusement le fichier et le contrôleur répondrait « aucun fichier reçu » — un message trompeur qui enverrait l'utilisateur chercher au mauvais endroit.

✅ Nº 5 — Gestion du stock

Le décrément est atomique : la condition fait partie du filtre de la requête.

async decrementStock(productId: string, quantity: number): Promise<boolean> {
  const result = await this.productModel.updateOne(
    { _id: productId, stock: { $gte: quantity } },   // ← la garde est dans le filtre
    { $inc: { stock: -quantity } },
  ).exec();
  return result.modifiedCount === 1;
}

Deux commandes simultanées ne peuvent donc pas faire passer le stock sous zéro : MongoDB applique les deux updateOne en série, et la seconde ne trouve aucun document correspondant. Une vérification en deux temps (lire puis écrire) laisserait au contraire une fenêtre de concurrence.

checkout() réserve le stock article par article, avec compensation en cas d'échec :

const reserved = [];
let ordersCreated = false;
try {
  for (const cartItem of cart.items) {
    if (product.type === 'physical') {
      const ok = await this.productsService.decrementStock(/* … */);
      if (!ok) throw new BadRequestException(`Stock insuffisant pour « ${product.title} »`);
      reserved.push({ productId, quantity });
    }
    /* … regroupement par vendeur + type … */
  }
  const orders = await Promise.all(/* … */);
  ordersCreated = true;
  await this.cartService.clearCart(buyerId);
  return orders;
} catch (err) {
  if (!ordersCreated) await this.releaseReservations(reserved);
  throw err;
}
Pourquoi le drapeau ordersCreated ? Une fois les commandes enregistrées, la réservation de stock leur appartient. Restituer le stock à ce stade créerait exactement la survente que l'on cherche à empêcher : les articles seraient remis en rayon alors qu'ils sont déjà vendus. La compensation ne doit donc s'appliquer qu'aux échecs survenus avant la création des commandes.

L'annulation restitue symétriquement le stock. Les deux seuls statuts annulables — pending_payment et processing — sont tous deux postérieurs au checkout, donc le stock a bien été décompté dans les deux cas.

✅ Nº 6 — Le prix promotionnel est appliqué

const hasPromo = product.promoPrice != null && product.promoPrice < product.price;
const unitPrice = hasPromo ? product.promoPrice! : product.price;

items.push({
  price: unitPrice,                                    // ce qui est facturé
  ...(hasPromo ? { originalPrice: product.price } : {}), // le prix barré
  subtotal: unitPrice * cart[productId],
});

La convention retenue : price est toujours le montant réellement facturé, et originalPrice n'apparaît que lorsqu'une promotion s'applique. Le frontend n'a donc aucun arbitrage à faire — il affiche price, et barre originalPrice s'il est présent.

Le test promoPrice < price évite qu'une « promotion » saisie par erreur au-dessus du prix normal ne majore la facture. Comme OrderItem fige cartItem.price au checkout, c'est bien le prix promo qui est gravé dans la commande.

✅ Nº 7 — Les emails ne font plus échouer les opérations

À l'inscription, l'échec d'envoi est journalisé sans interrompre le flux : le compte étant déjà créé, propager l'erreur afficherait un échec à un utilisateur dont le compte existe — et qui ne pourrait plus se réinscrire (409 Conflict). 

try {
  await this.emailService.sendWelcomeEmail(user.email, user.name);
} catch (err) {
  this.logger.warn(`Email de bienvenue non envoyé à ${user.email}`, /* … */);
}

Dans deliverDigitalItems(), le try/catch est placé à l'intérieur de la boucle : un envoi défaillant ne prive plus l'acheteur des articles suivants de la même commande.

8. État du frontend & suite

Cette section proposait à l'origine une structure de frontend, à un moment où frontend/src/ ne contenait que le squelette Vite par défaut. Ce n'est plus le cas : l'authentification, le catalogue public, la gestion des catégories et la gestion des produits côté vendeur sont construits et câblés contre cette API. Le détail complet — fichier par fichier, ce qui fonctionne, ce qui est une coquille vide, ce qui manque encore, et les conventions déjà en place à respecter pour la suite — vit désormais dans son propre document :

docs/frontend-dossier-technique.html À lire avant toute reprise du travail sur le panier, les commandes ou les paiements. Il documente notamment que features/cart/cartApi.ts n'a aujourd'hui qu'une lecture seule (getCart) malgré les cinq routes disponibles ci-dessus, qu'aucune couche ordersApi/paymentsApi n'existe encore, et que les boutons « Ajouter au panier » du catalogue sont déjà présents visuellement mais non branchés.

Deux rappels de cette section qui restent valables et qu'un futur agent doit garder en tête :

  • Le checkout renvoie un tableau de commandes, jamais une seule (§6.1) — un panier avec plusieurs vendeurs, ou un même vendeur avec du physique et du numérique, produit plusieurs Order en un seul appel à POST /orders/checkout.
  • Les routes du panier renvoient l'état complet à chaque mutation (§5.5) — un futur câblage de addItem/updateItem/removeItem devrait patcher le cache RTK Query directement plutôt qu'invalider et recharger.
En résumé Le backend est solidement structuré : séparation nette des modules, validation stricte, règles métier centralisées au bon endroit, instantanés de commande bien pensés, idempotence du webhook gérée. Les huit points relevés à l'audit ont tous été corrigés et vérifiés (section 7) — aucun ne remettait en cause l'architecture. Le contrat d'API n'a connu depuis qu'une seule évolution, documentée ci-dessus : la saisie des coordonnées de livraison au checkout (7 août 2026). La suite du frontend peut s'appuyer dessus sans réserve.
Ce qui reste hors périmètre Deux points connus n'ont volontairement pas été traités, car ils dépassent la correction de bugs. Les liens de téléchargement numériques (§6.5) exposent toujours le fileKey brut : il faudrait des URLs signées à durée limitée et un compteur appliquant downloadLimit. Les frais de port sont saisissables via shippingOptions, mais ne sont toujours ni choisis au checkout ni ajoutés au total : l'ajout de shipping (7 août 2026) a réglé où livrer, pas combien facturer pour le faire. Les deux méritent d'être décidés avant la mise en production.
Également non traité par la mise à jour du 7 août 2026 L'adresse collectée n'est ni transmise à Stripe (paymentIntents.create() ne reçoit toujours que amount, currency et metadata — donc ni shipping ni receipt_email), ni envoyée par email au vendeur : il n'existe toujours aucun email de commande hormis la livraison numérique (§4). Le vendeur consulte l'adresse dans l'interface, via GET /orders/:id. Enfin, elle n'est pas mémorisée sur le profil — le modèle User est inchangé et chaque checkout la redemande.
